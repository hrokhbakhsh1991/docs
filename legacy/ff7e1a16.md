## [Audit 13] Discovered Ghost Fields (Template-Only Outliers)

**Review date:** 2026-05-31  
**Severity:** High — 4 of 52 Settings overlay rows (~7.7%) have **no editable input** in the six Denali create-wizard section components; admins configure rules for fields staff cannot set during tour creation  
**Scope:** `listDenaliTemplateStorageFieldPaths()` vs JSX in `DenaliBasicInfoSection`, `DenaliProgramNatureSection`, `DenaliLogisticsSection`, `DenaliPricingSection`, `DenaliLegalSection`, `DenaliPhotosSection` (create flow via `WizardStepBody`; **excludes** `DenaliReviewStep`)  
**Code changes in this audit:** None (analysis only)

### Executive summary

The Settings template overlay table is populated exclusively from `listDenaliTemplateStorageFieldPaths()` in `@repo/denali-domain`, which unions every unique `path` across the generated `denaliRuleSet` and normalizes each through `toDenaliTemplateStoragePath()` (`packages/denali-domain/src/rules/listDenaliTemplateStorageFieldPaths.ts`).

Cross-referencing all **52** storage paths against the six section files under `apps/web/src/features/tours/denali/sections/` (plus widgets they compose) yields **48 paths with a corresponding visual control** and **4 ghost paths** with no input anywhere in the create-wizard section tree.

All four ghosts originate from registry rows in `packages/denali-domain/src/registry/denaliFieldRegistryData.ts` that **are** emitted into `packages/denali-domain/src/rules/generated/denaliRuleSet.generated.ts` via `pnpm --filter web generate:denali-wizard`, but were **never wired to section JSX** (or were deferred to review / implicit constants).

### 1. Methodology

| Step | Action |
|------|--------|
| 1 | Emitted sorted storage array from `listDenaliTemplateStorageFieldPaths()` (52 paths, runtime 2026-05-31) |
| 2 | Mapped each storage path → registry `canonicalPath` via `DENALI_FIELD_REGISTRY` + `toDenaliTemplateStoragePath` |
| 3 | Searched six section files and their direct widget imports for `isVisible(...)`, `updateCanonical`, `useController`, `register`, `data-field-path`, and `data-testid` bindings per path |
| 4 | Traced rule-model inclusion to `denaliRuleSet.generated.ts` and registry source rows |
| 5 | Excluded `DenaliReviewStep.tsx` per audit scope (review is step 7, not one of the six section files) |

**Create-wizard mount path (for context):** `WorkspaceTourWizard` → `WizardStepBody` → lazy step re-export → `Denali*Section` only. Does **not** use `DenaliSection` wrapper or `DenaliFieldRenderer` supplemental rows (those appear in tour **edit** flat layout only).

```text
denaliFieldRegistryData.ts          (authoritative field definitions)
        │  pnpm --filter web generate:denali-wizard
        ▼
denaliRuleSet.generated.ts          (category × duration field matrices)
        │  listDenaliRuleFieldPaths()
        ▼

        │  listDenaliTemplateStorageFieldPaths()
        ▼
Settings overlay table rows          (tour-wizard-template-builder-form.tsx)
```

**Leak mechanism:** Any path present in the generated rule set becomes a Settings table row automatically. There is **no UI parity filter** between registry/rule emission and Settings listing.

### 5. Per-ghost forensic notes

#### 5.1 `publishStatus`

- Registry tags: `core`, `zodKind: publishStatus`, `stepId: denali_basic` — misleading step assignment.
- Settings admins can set overlay visibility/required on a field that **only appears on the review rail step**, not basics.
- `useWizardStateGuard` / `usePublishButtonGuard` read `basicInfo.publishStatus` from form state set exclusively on review.

#### 5.2 `startPointLocationText`

- Tagged `optional_basic` in registry; rule model exposes it on basics step.
- No `Input`/`Textarea` in `DenaliBasicInfoSection.tsx` despite `basicInfo.startPointLocationText` in `denaliCore.schema.generated.ts` ~58.
- Distinct from `startPoint` location zone picker (which **does** exist in logistics).

#### 5.3 `pricing.paymentMode`

- Rule model marks **`required: true`** in all generated matrices — admins may mark overlay `required` for a field users never choose.
- Product decision: offline-only payments; UI replaced by static hint. Canonical/schema still accept `offline_receipt` only (`denaliCanonicalTourSchema.base.ts` ~82).

#### 5.4 `transport.transportNotes`

- Full registry wire to API `transportationNotes`.
- Logistics section renders mode, cost, personal car, dong, admin capacity — **notes textarea never implemented** in section JSX.
- Dead focus bridge suggests planned widget was never shipped.

### 10. Conclusion

The Settings template grid is a **faithful mirror of the generated Denali rule set**, not of the **shipped create-wizard UI**. Four storage paths leak through codegen into overlay configuration without any corresponding input in the six section components: **`publishStatus`**, **`startPointLocationText`**, **`pricing.paymentMode`**, and **`transport.transportNotes`**. All four trace to `denaliFieldRegistryData.ts` → `denaliRuleSet.generated.ts` → `listDenaliTemplateStorageFieldPaths()`. Until registry, UI, and Settings listing are aligned, admins will configure visibility/required rules for fields staff cannot edit during tour creation.

## [Audit 14] Profile Exclusions & Asymmetric Template Exposure

**Review date:** 2026-05-31  
**Severity:** High — `denali_pilot` does **not** use classic profile field-group stripping, yet the Settings template surface exposes **all 52 rule-model overlay rows and a broader canonical JSON schema** with **zero profile or matrix filtering**, while the create wizard applies **category×duration rule matrices, normalization clears, capability gates, and denali_pilot-only publish/submit strips** at runtime  
**Scope:** `packages/types/src/tour-form-profile-descriptors.ts` (`denali_pilot` row), `packages/shared-contracts/src/tours/workspace-ui-capabilities.ts`, Denali normalization/submit strip paths, `denaliCanonicalTemplateDataSchema` vs `listDenaliTemplateStorageFieldPaths()`, Settings template builder  
**Code changes in this audit:** None (analysis only)

### Executive summary

A common misconception is that `denali_pilot` “strips fields” via `tour-form-profile-descriptors.ts` the way `urban_event` or `cinema_event` do. **It does not.** The `denali_pilot` descriptor row sets `inactiveFieldGroups: []` and `clearsTripDetailsRoots: []` — the most permissive structural profile in the table (`packages/types/src/tour-form-profile-descriptors.ts` ~344–363).

Asymmetric hiding instead comes from **three downstream layers** the Settings builder ignores:

1. **Denali rule matrix** (category × duration) — drives `isVisible` / `hidden` in `denaliRuleSet.generated.ts`; `normalizeDenaliWizardForm` **clears** values for non-visible paths.
2. **`denali_pilot` UI capability flags** — geo publish gate, single-day logistics strip on submit, theme category filter, peak-experience and custom-services contextual visibility (`workspace-ui-capabilities.ts` ~58–65).
3. **Contextual field rules** — transport dong/cost, peak experience, custom services (`denaliContextualRules.ts` + registry `contextualVisibility`).

Meanwhile Settings exposes:

- **Overlay table:** all paths from `listDenaliTemplateStorageFieldPaths()` (52 rows) — no `getInactiveFieldGroupsForProfile`, no matrix filter, no `workspaceFormProfile` gate.
- **Canonical JSON:** `denaliCanonicalTemplateDataSchema` — accepts top-level keys **not present** in the overlay table (e.g. `duration`, `meetingPoint`, `customServiceLabels`, `overview.nonAttendanceDetails`).

**Verdict:** Template configuration is **superset-unfiltered**; wizard execution is **profile-aware + matrix-filtered + normalize-stripped**. Admins can author overlay rules and JSON seeds for fields the wizard will hide or delete once staff pick a tour category/duration.

## [Audit 15] Registry Pruning Blueprint & Contract Synchronization

**Review date:** 2026-05-31  
**Severity:** Critical — Settings overlay rows are derived from the **generated rule-model union** (52 paths), not from **create-wizard section bindings** (48 editable + 4 ghosts); seven registry rows with `inRuleModel: false` have wizard UI but **no overlay row**, and four rule-model rows have overlay UI but **no section input**  
**Scope:** `packages/denali-domain/src/registry/denaliFieldRegistryData.ts`, `denaliRegistryCodegen.ts`, `listDenaliTemplateStorageFieldPaths.ts`, `generate-denali-wizard-config.ts`, `@repo/types` template schema, Settings/API overlay validators  
**Code changes in this audit:** None (analysis only)

### Executive summary

The Settings template table is **not** fed directly from `DENALI_FIELD_DEFINITIONS`. It is fed from a **second-hop projection**:

```text
denaliFieldRegistryData.ts (59 rows)
        │  fieldInCell(): skips inRuleModel === false
        ▼
buildDenaliRuleSetFromRegistry()  →  denaliRuleSet.generated.ts
        │  listDenaliRuleFieldPaths(): union across all matrix cells
        ▼
toDenaliTemplateStoragePath()     →  listDenaliTemplateStorageFieldPaths()
        ▼
Settings overlay table + API overlay allow-list (52 rows today)
```

**`inRuleModel: false` is working as designed** — it prevents codegen emission. The seven excluded paths do **not** appear in Settings. The real defects are:

1. **Forward leakage:** four paths with `inRuleModel !== false` and matrix tags (`core` / `optional_basic`) emit into the rule set but have **no create-wizard section control** (Audit 13 ghosts).
2. **Reverse leakage:** five paths with **live section widgets** stay `inRuleModel: false` and are **absent** from the overlay table while still valid in `denaliCanonicalTemplateDataSchema`.
3. **Contract fork:** template save schema (`denaliCanonicalTemplateDataSchema.ts`) and overlay allow-list (`listDenaliTemplateStorageFieldPaths`) are maintained on **different derivation paths** with no enforced bijection to section JSX.

**Target contract (1:1 mirror):** overlay rows = `{ storage paths bound by create-wizard section JSX in steps 1–6 }` — currently **48 rows**, plus explicit buckets for review-only / implicit constants if product requires them.

#### 1.1 Why `inRuleModel: false` rows do **not** leak (correct behavior)

```typescript
export function fieldInCell(def: DenaliFieldDefinition, cell: DenaliMatrixCell): boolean {
  const cellTags = DENALI_MATRIX_CELL_TAGS[cell];
  if (cellTags == null) return false;
  if (def.inRuleModel === false) return false;  // ← hard stop
  if (def.tags.length === 0) return false;
```

**Codegen does not leak `inRuleModel: false` fields into Settings** — the gate in `denaliRegistryCodegen.ts` is correct. Leakage occurs because **Settings uses the full rule-model union** as its allow-list, and the rule model includes **every tagged row with default `inRuleModel`**, including four paths never bound to create-wizard sections. Meanwhile, **five live UI paths are deliberately excluded** via `inRuleModel: false`, creating inverse drift from the canonical JSON schema.

The surgical fix is **not** to delete registry rows but to **split contracts**:

1. **Rule model** — continues to drive wizard visibility/normalization (may shrink when ghosts get `inRuleModel: false`).
2. **Overlay allow-list** — new derived function keyed off section bindings + explicit surface metadata.
3. **Template JSON schema** — superset for hydration, with deprecated keys documented but not overlay-editable.

After Phases 1–3, the Settings table becomes a **mathematically exact mirror** of the Denali creation layout (48 or 53 paths, product choice), while saved workspace templates remain loadable via tolerant overlay parsing and unchanged canonical JSON validation.

## [Audit 18] Codegen Metadata Leakage & Registry Invariants

**Review date:** 2026-05-31  
**Severity:** Critical — **`inRuleModel: false` and legacy rows do not leak into `listDenaliTemplateStorageFieldPaths()`**, but the codegen pipeline emits **multiple downstream artifacts with different supersets** (59-path canonical map, 59-row Zod slices, 52-path rule union, 358 duplicated matrix rows in `denaliRuleSet.generated.ts`), creating the appearance that deprecated/profile metadata is “bundled” into runtime template paths  
**Scope:** `denaliFieldRegistryData.ts`, `denaliRuleMatrixRecipes.ts`, `denaliRegistryCodegen.ts`, `generate-denali-wizard-config.ts`, generated artifacts under `packages/denali-domain/src/rules/generated/` and `schemas/`  
**Code changes in this audit:** None (analysis only)

### Executive summary

There is **no JSON schema or decorator layer** driving Denali wizard codegen. The pipeline is entirely **TypeScript dictionary → pure functions → committed `.generated.ts` files**.

Runtime **`listDenaliTemplateStorageFieldPaths()`** (52 paths) is a **strict subset** of the registry (59 rows):

| `denaliRuleSet.generated.ts` field row instances | **~358** | 52 unique paths × 7 matrix cells (duplicate metadata per cell) |

**Verdict:** Fields flagged `inRuleModel: false` or legacy (`meetingPoint`, `gatheringPoint`) are **not appended** to the template paths array. ### 4. Why `denaliRuleSet.generated.ts` looks “over-bundled”

#### 4.1 Cross-cell union (category archetypes, not workspace profiles)

The generated file materializes **every** active category × duration cell (`mountain`, `nature`, `desert`, `event` × `single_day`/`multi_day`). Each cell repeats ~51 field rows with cell-specific `required`/`hidden` from `resolveRuleRow()` + `cellOverrides`.

`listDenaliRuleFieldPaths()` then **unions** paths across cells → **52 unique** keys fed to Settings.

This is **tour classification matrix aggregation**, not `urban_event` / `cinema_event` workspace profile metadata. An admin configuring a template sees rows for **mountain-only**, **event-only**, and **shared core** fields simultaneously — even though staff only see the subset for their selected category/duration at runtime.

#### 4.2 Per-cell duplication inflates generated file size

| Metric | Value |
|--------|-------|
| Unique canonical paths in rule set | **52** |
| Matrix cells with models | **7** |
| Total `{ path, required, hidden, step }` rows in `denaliRuleSet.generated.ts` | **~358** |

### 9. Conclusion

The Denali codegen pipeline has a **single human-edited field dictionary** (`denaliFieldRegistryData.ts`) and a **matrix tag recipe file** (`denaliRuleMatrixRecipes.ts`). The `fieldInCell` invariant **correctly excludes** all seven `inRuleModel: false` rows from `denaliRuleSet.generated.ts` and therefore from `listDenaliTemplateStorageFieldPaths()`.

The appearance of metadata leakage comes from:

1. **Settings consuming the cross-cell rule-path union** (52 paths) instead of a category×duration slice or section-binding list;
2. **Sibling generated artifacts** (59-key canonical map, full Zod schema) that intentionally retain legacy/hydrate fields without `fieldInCell` filtering;
3. **Four ghost paths** that pass the rule-model gate (`core` tags) but lack section JSX;
4. **~358 duplicated matrix rows** in the committed generated file — structural verbosity, not extra unique fields;
5. **No profile archetype input** to codegen — workspace profile effects are runtime-only.

Remediation (documentation cross-ref Audit 15): decouple overlay allow-list from raw `listDenaliRuleFieldPaths()`, set `inRuleModel: false` on ghost rows or wire UI, prune orphan `transport_notes` recipe tag, and add CI guard equating template storage paths to create-wizard surface bindings.

## [Audit 19] Conditional Path Dependencies & Matrix Conflicts

**Review date:** 2026-05-31  
**Severity:** High — Settings overlay table is a **flat, un-gated 52-row list** with no category, duration, transport-mode, or payment-context selectors; runtime wizard applies a **three-layer visibility stack** (contextual rules → merged overlay `hidden` → section JSX gates) that Settings does not model, producing **silent rule conflicts** when admins configure requiredness for contextually hidden fields  
**Scope:** `tour-wizard-template-builder-form.tsx`, `templateOverlay.ts`, `denaliContextualRules.ts`, `denaliFieldGate.ts`, `denaliUIAdapter.ts`, `denaliFieldRegistryData.ts`, Denali section components  
**Code changes in this audit:** None (analysis only)

### Executive summary

| Surface | Conditional awareness |
|---------|------------------------|
| **Settings overlay table** | **None** — `fieldPaths.map()` renders all 52 storage paths with visibility/required `<Select>` (~174–213) |

### 5. Evaluation conflicts (overlay ↔ runtime ↔ sections)

#### 5.0 Overlay vs contextual precedence — `program.itinerary` & `transport.dongAmount` (Task 1)

Both paths appear as unconditional rows in Settings. Runtime outcome depends on **evaluation order** in `isDenaliFieldVisibleOnStep` / `isDenaliFieldVisibleInModel`:

```text
Contextual (evaluateDenaliContextualVisibility)  →  HARD STOP if false
        ↓ pass
Matrix row hidden (overlay-merged field.hidden)  →  STOP if true
        ↓ pass
Step assignment (field.step === step)
```

| Admin overlay | Field | Contextual rule? | Matrix default (example cell) | Runtime visibility | Runtime required | Admin intent honored? |
|---------------|-------|------------------|------------------------------|-------------------|------------------|----------------------|
| `visibility: always` | `program.itinerary` | **None** | `mountain:single_day` → `hidden: true` | **Visible** — overlay sets `hidden: false` on **all 7 cells** (`templateOverlay.ts` ~77–78) | Follows overlay `required` if set | **Yes — overrides matrix** (Conflict A) |
| `required: required` | `program.itinerary` | None | Multi-day → already required | Visible when overlay/marketing forces single-day visible | **Required** when visible | Yes on forced-visible cells |
| `visibility: always` | `transport.dongAmount` | **`transportDongVisible`** | Visible in matrix when in cell | **Hidden** if mode ≠ `shared_cars` / personal-car path — contextual runs **before** matrix `hidden` (`denaliUIAdapter.ts` ~175) | N/A when hidden | **No — contextual wins** |
| `required: required` | `transport.dongAmount` | **`transportDongVisible` + required variant** | Row may show `required: true` after merge | Hidden when transport gate false | `isDenaliFieldRequired` returns false when not visible (`denaliFieldGate.ts` ~35–37) | **No — silent no-op** (Conflict B) |
| `visibility: hidden` | `transport.dongAmount` | Same | — | Hidden (overlay + contextual) | Not required | Yes |
| inherit (empty) | `transport.dongAmount` | Same | Visible in matrix | Visible only when `isDenaliTransportDongAmountVisible(...)` | Contextual required when visible + shared_cars path | Matches designed transport UX |

**Overlay merge scope:** `applyOverlayToRuleSet` applies identical patches to **every non-null matrix cell** (~98–120) — admin cannot target `mountain:multi_day` only. A `program.itinerary → always` patch therefore affects **event single-day** cells equally, not just the admin’s mental “multi-day itinerary” use case.

**Requiredness trap:** Overlay only sets boolean `field.required` (~82–86); it does **not** inject contextual predicates. `required: required` on `transport.dongAmount` marks the matrix row required in all cells, but **`isDenaliFieldRequired` still short-circuits on visibility** — staff never see a required dong field under `organizer_vehicle`, and normalize **strips any seeded dong value** (`denaliRuleAccess.spec.ts` ~36–43).

#### Conflict A — Overlay **`visibility: always`** vs matrix **`hidden: true`**

**Mechanism:** `applyOverlayToField` (`templateOverlay.ts` ~74–78) sets `hidden = false` when patch visibility is `always` or `active`. `applyOverlayToRuleSet` applies the **same patch to all seven matrix cells** (~98–120).

**Example:** Admin sets `program.itinerary` → `visibility: always`. Base rule model has `hidden: true` on `mountain:single_day`. After merge, **single-day mountain** cell also gets `hidden: false`.

**Runtime:** `isDenaliFieldVisibleOnStep` respects merged `hidden` (contextual passes) → **itinerary can appear on single-day tours** despite matrix design.

**Severity:** **High** — overlay **overrides** classification matrix; Settings gives no warning that `always` is global across all category×duration cells.

#### Conflict B — Overlay **`required: required`** vs **contextual visibility**

**Mechanism:** Contextual check runs **before** matrix `hidden` (`denaliUIAdapter.ts` ~175). If contextual fails, field is not visible and not required.

**Example:** Admin sets `transport.dongAmount` → `required: required`. Staff selects `organizer_vehicle`. `transportDongVisible` → false.

**Runtime:** `DenaliLogisticsSection.tsx` ~48–49, ~154–171 — `showDongAmount` false; dong input not rendered; value cleared on normalize.

**Severity:** **Medium** — admin rule is **silently inert**; no validation error at template save time.

#### Conflict C — Overlay vs **section composite gates**

**Mechanism:** Sections sometimes batch paths with `arePathsVisible`:

```typescript
// DenaliProgramNatureSection.tsx ~31–34
const showOutdoorProgram = arePathsVisible(
  ["program.difficultyLevel", "program.hikingHoursApprox"],
  form,
);
```

**Example:** Overlay sets `program.difficultyLevel` → `always` but `program.hikingHoursApprox` remains matrix-hidden for an event tour. Composite block **hidden** even though one field forced visible.

**Severity:** **Low** — partial overlay on grouped UI blocks produces inconsistent section bodies.

#### Conflict D — **`inherit`** vs staff classification not yet chosen

**Mechanism:** Preview/create forms may have empty `basicInfo.tourType` → `resolveDenaliRuleModelFromForm` returns `null` (`resolveRuleModel.ts` ~48–54). `getDenaliUIFromForm` falls back with `ruleModel: null` (~301–303).

**Settings:** Table still lists all 52 paths; preview may show **basics-only** visibility until category/duration selected in preview form.

**Severity:** **Medium** — preview misleads admins about post-classification visibility.

#### Conflict E — Template save vs runtime normalize on **canonical JSON seeds**

**Mechanism:** `denaliCanonicalTemplateDataSchema` accepts keys regardless of future visibility. `normalizeDenaliWizardForm` clears non-visible paths after staff pick category/transport.

**Example:** Template JSON seeds `transport.dongAmount: 50000`; staff uses non–shared-car mode → value cleared.

**Severity:** **Medium** — template seeds for conditional fields may **vanish** at runtime without admin feedback.

#### Conflict F — **`visibility: hidden`** overlay vs contextual “registry-only” paths

**Mechanism:** For paths with `contextualVisibility` but absent from a matrix cell, `isDenaliFieldVisibleInModel` can still return true via registry-only branch (`denaliFieldGate.ts` ~22–25). Overlay `hidden` on matrix row does not affect registry-only contextual paths consistently.

**Severity:** **Low** — edge case for `inRuleModel: false` rows (mostly absent from overlay table).

### 3. Proposed unpacked form shape

#### 3.1 Recommended RHF type (v2)

Extend `TourWizardTemplateBuilderFormValues`:

```typescript
type TourWizardTemplateBuilderFormValues = {
  fieldRulesOverlay: Record<string, { visibility: string; required: string }>;
  /** @deprecated transitional — remove after migration */
  canonicalDataJson?: string;
  /** Flat leaf values keyed by template storage path (same vocabulary as overlay table). */
  canonicalData: Record<string, unknown>;
};
```

**Registration pattern (mirror overlay):**

```typescript
function canonicalSeedRegistrationPath(storagePath: string): FieldPath<TourWizardTemplateBuilderFormValues> {
  return `canonicalData[${storagePath}]` as FieldPath<TourWizardTemplateBuilderFormValues>;
}
```

Examples:

| Storage path | RHF path | Example widget |
|--------------|----------|----------------|
| `title` | `canonicalData[title]` | plain `Input` |
| `destinationId` | `canonicalData[destinationId]` | `DestinationCombobox` |
| `overview.peakHeight` | `canonicalData[overview.peakHeight]` | `PersianNumberInput` |
| `program.themeIds` | `canonicalData[program.themeIds]` | multi-select / checkbox group |
| `transport.mode` | `canonicalData[transport.mode]` | enum `Select` |

#### 3.2 Pack / unpack functions (submit boundary)

| Function | Input | Output | Location (proposed) |
|----------|-------|--------|---------------------|
| `unpackCanonicalTemplateToFormValues` | `DenaliCanonicalTemplateData` + path list | `Record<string, unknown>` flat leaves | new helper adjacent to `tour-wizard-template-builder-form.ts` |
| `packCanonicalFormValuesToTemplateData` | flat `canonicalData` record | `DenaliCanonicalTemplateData` nested object | uses inverse of `toDenaliTemplateStoragePath` + nested setters for containers |

**Unpack algorithm:**

1. Start from `template.canonicalData` object (not string).
2. For each path in **`listCanonicalTemplateSeedPaths()`** (new: schema leaf enumerator or Layer C + nested expansions):
   - Read value via `getDenaliCanonicalPathValue(canonical, path)` (existing in preview path utils) or dot-walk.
   - Set `canonicalData[path] = value ?? ""` (or `undefined` omitted).
3. Omit keys with `undefined` on pack.

**Pack algorithm:**

1. Iterate `Object.entries(values.canonicalData)`.
2. Skip empty strings / undefined (partial template semantics preserved).
3. **`setDenaliCanonicalPathValue(out, storagePath, value)`** — nest into `overview.peakHeight`, `program.themeIds`, etc.
4. Run **`validateDenaliCanonicalTemplateData(packed)`** before API submit.

### 5. Component reuse blueprint

#### 5.1 Architecture (recommended)

```
TourWizardTemplateBuilderForm (existing RHF)
├── fieldRulesOverlay[...]          (unchanged)
├── canonicalData[storagePath]      (Audit 24 flat map)
└── DenaliTemplateSeedFieldsPanel
    ├── useTourDestinations()       ← catalog boundary (page/section)
    ├── useWorkspaceTourCrewMembers() (if seeding leaderUserIds)
    └── per-path DenaliTemplateSeedField
            ├── zodKind → widget map
            ├── Controller → canonicalData[path]
            └── pack() on submit
```

**Do not** nest `DenaliCanonicalProvider` on the left — avoids dual canonical stores and wizard/templat path mismatch (`basicInfo.startPoint` vs JSONB `startPoint`).

#### 5.2 Widget → adapter mapping

| Registry / path | Mount | Adapter responsibilities |
|-----------------|-------|---------------------------|
| `destinationId` | `DestinationCombobox` | `useTourDestinations()` options; `Controller` on `canonicalData[destinationId]`; optional altitude → `canonicalData[overview.peakHeight]`; optional QuickAdd wrapper |
| `overview.peakHeight`, `capacityMax`, `metrics.elevationGain`, pricing ints, etc. | `PersianNumberInput` | `Controller`; string ↔ number coerce; `formatThousands` where wizard uses it (~209–211) |
| `startPoint`, `summitPoint`, `campPoint`, `endPoint` | `DenaliLocationPickerEditor` | **Not** `DenaliLocationZoneField`; one editor per zone; value from packed location object; `patch` → update nested object in flat map or sub-key `canonicalData._obj.startPoint`; i18n labels from `useTranslations("tours.denali")` |
| `leaderUserIds` | `DestinationCombobox` `multiple` | Crew options from `useWorkspaceTourCrewMembers()` |
| `program.themeIds`, enums | `Select` / catalog hooks | Separate hooks (`useSettingsTourThemes`, etc.) at panel boundary |
| `photos`, `itinerary`, `gatheringPoints` | Defer Phase 2 | Composite widgets; keep JSON sub-editor or preview-only until unpack supports containers |

#### 5.3 Wrapper boundaries

| Wrapper | Purpose |
|---------|---------|
| **`DenaliTemplateSeedField`** | Maps `storagePath` + `zodKind` → leaf widget; `Controller` bind; error from `formState.errors.canonicalData?.[path]` |
| **`DenaliTemplateCatalogProviders`** | Optional: `QuickAddModalProvider` only (preview already has it; left panel needs it for destination quick-add) |
| **`TemplateLocationSeedEditor`** | Thin fork of `DenaliLocationZoneEditor` **without** `useDenaliCanonical` — only `value` + `onChange` props |
| **`mapDenaliValidationToSeedPath`** | Extend Audit 24 error mapper for `canonicalData.{path}` |

#### 5.4 Preview sync (right panel unchanged initially)

| Phase | Left writes | Right reads |
|-------|-------------|-------------|
| 1 | Structured `canonicalData` | `pack(canonicalData)` passed as prop instead of JSON string (Audit 24 §5) |
| 2 | Same | Preview `tryHydrateCanonicalTemplate` unchanged — still wizard form + `DenaliCanonicalProvider` |

Left-panel edits **must not** require preview's canonical context; one-directional hydrate remains valid.

#### 5.5 What breaks if mounted naïvely

| Mistake | Failure mode |
|---------|--------------|
| Mount `DenaliLocationZoneField` without wizard `FormProvider` | **`useFormContext` throws** |
| Mount `DenaliBasicInfoSection` on left | Writes **`basicInfo.*`** + **`updateCanonical`** — not persisted to template API |
| Mount `DenaliCanonicalFieldControl` for `destinationId` | **Renders nothing** (null) |
| Skip `useTourDestinations` on left | Combobox with **empty options** — admins cannot pick real destinations |
| Dual `DenaliCanonicalProvider` left + right | **Split brain** — left template save ignores preview canonical state |

### 8. Conclusion

**`DestinationCombobox`** and **`PersianNumberInput`** are **already extractable** — controlled, catalog-agnostic leaves with proven settings-form reuse. **`DenaliLocationPickerEditor`** is extractable **without** the zone field shell. **`DenaliLocationZonesSection`** is **not** drop-in: it hard-codes wizard RHF paths and canonical dual-write. The safe blueprint is a **`DenaliTemplateSeedField` adapter layer** on the left that owns **catalog queries at the panel boundary**, binds **`canonicalData[storagePath]`** via `Controller`, and mounts **leaf widgets only** — preserving real destination and geocoding catalog bindings without importing the wizard's canonical context tree.
