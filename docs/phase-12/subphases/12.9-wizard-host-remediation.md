## Phase 7 — Submit error hardening (2026-08-05)

### Problem statement

Recent operator smoke runs exposed three UX/robustness gaps in wizard error handling:

- submit paths handled `{ ok: false }` API responses, but uncaught async exceptions could bypass user-facing error state
- stale submit alerts remained visible after users edited draft fields
- decode/parse fallthrough could surface raw error tokens instead of safe localized copy

### Applied strategy

1. **Exception-safe submit orchestration**
   - Wrap async submit flows in create and flat-edit orchestrators with `try/catch`.
   - On catch, force a product-blind encoded fallback (`unknown_error`) so footer alert always renders deterministic copy.
2. **Stale-error eviction on canonical draft change**
   - Compute stable draft data keys and clear submit error state when canonical payload changes after a failed submit.
   - Preserve first-render behavior and avoid false clears on identity-only remints.
3. **Safe message fallback contract**
   - Resolver no longer returns raw wire tokens when decode fails.
   - Fall back to localized `submit.errorUnknown` / `submitEdit.errorUnknown`.
4. **Translation guard for optional details**
   - Error detail rows (`code`, `message`, `correlationId`) only render when translator confirms key presence.
5. **No duplicate validation messaging**
   - When field-level `submitValidationIssues` are present, footer `submitError` summary is suppressed (create view + flat-edit page).

### Validation contract

- create/flat-edit submit exceptions produce deterministic footer alert (no silent failure)
- editing any field after submit failure clears stale submit alert state
- malformed submit raw token never reaches operator-visible UI
- localized detail rows degrade gracefully when translation keys are absent
- validation-issue list and footer summary are mutually exclusive (no double alert)
